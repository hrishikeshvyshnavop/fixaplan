# CMS (Payload)

The site runs [Payload 3](https://payloadcms.com) inside the Next.js app. Right now it stores
waitlist signups and the FAQ text, and adds an admin panel. The rest of the page's copy is still in
the code.

- **Admin panel:** `/admin` (first visit asks you to create an admin user)
- **REST API:** `/api/...` (GraphQL at `/api/graphql`)
- **Database:** Supabase Postgres, project `fixaplan` (ref `cpuxbslhldggplbmdgpv`). See [supabase.md](supabase.md)

Versions: `payload` / `@payloadcms/*` 3.90.2 on Next 16.3.5 (Payload supports Next `>=16.3.3 <17`).

---

## Setup (new machine)

1. `npm install`
2. Create `.env` in the project root (it is git-ignored, so it's not in the repo):
   ```
   DATABASE_URL=postgresql://postgres.cpuxbslhldggplbmdgpv:<PASSWORD>@aws-0-us-east-1.pooler.supabase.com:5432/postgres
   PAYLOAD_SECRET=<long random string>
   ```
   Generate a secret with
   `node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"`.
   Keep the same secret, or existing admin logins stop working.
3. `npm run dev` and open `http://localhost:3000/admin` to create the first admin user.

## Where things are

| Path | What |
|---|---|
| `payload.config.ts` | Payload config: collections, globals, Postgres adapter, secret, migrations |
| `collections/Users.ts` | Admin accounts (email + password) |
| `collections/Waitlist.ts` | Signups: `email` (unique), `name`, automatic `createdAt` |
| `collections/Media.ts` | Uploaded images. Files go to the public Supabase Storage bucket `media` (S3 API, `@payloadcms/storage-s3`); the page links to their public URL and `next/image` resizes them |
| `globals/Faq.ts` | FAQ text (intro, email chip, questions). Defaults are today's copy; saving refreshes `/` |
| `app/(frontend)/` | The public site: `layout.tsx`, `page.tsx`, `globals.css`, `fonts/`, `opengraph-image.png` |
| `app/(payload)/` | Admin panel and API routes. Generated by Payload; don't edit by hand |
| `app/waitlist/store.ts` | `addSignup()` saves a signup to the `waitlist` collection |
| `migrations/` | Database migrations; production runs them on startup |
| `payload-types.ts` | Generated TypeScript types for the collections |

`app/components/`, `app/waitlist/` and `app/site.ts` stay in `app/`. They aren't routes, so
the `@/app/...` imports didn't change.

## How a signup is saved

1. The modal posts to the server action `joinWaitlist` (`app/waitlist/actions.ts`). The action
   still does the honeypot check and email validation.
2. `addSignup()` looks the email up. Emails are lowercased first, so `A@x.com` and `a@x.com`
   count as the same person.
3. New emails are created with `overrideAccess`. If the same email arrives twice at the same
   moment, the unique index rejects the second one and it is treated as already on the list.
4. The place in line is the number of signups created at or before this one.

**Access:** the public API can't create, read, change or delete signups (`/api/waitlist`
returns 403). Only logged-in admins can see them in `/admin`, where they can be exported.

## Editing the FAQ

- `/admin` → **Globals** → **FAQ**: the intro line, the chip text and link, the text after the
  chip, and the questions (add, remove, drag to reorder).
- The homepage reads it with `payload.findGlobal({ slug: "faq" })` in `app/(frontend)/page.tsx`,
  and the JSON-LD `FAQPage` uses the same questions. Until the global is saved once (or if a field is
  left empty), `FAQ_DEFAULTS` in `globals/Faq.ts` is shown.
- `/` stays static. The global's `afterChange` hook calls `revalidatePath("/")`, so the next visit
  after a save gets the new text.
- Anyone can read it (`GET /api/globals/faq`); only logged-in admins can change it (anonymous
  updates return 403).
- Checked on a production build with a fresh database: an edit through the API showed on the next
  load of `/`, in both the section and the JSON-LD.

## Images (Media)

- Upload in `/admin` → **Media**, or straight from an upload field such as the FAQ's
  **Chip hover image**. PNG, JPEG, WebP, AVIF or GIF, up to 5 MB. No SVG: `next/image` refuses it.
- Files are stored in the Supabase bucket `media` (public, created with SQL on
  `storage.buckets`). Payload writes to it through Supabase's S3 API with an access key made in the
  dashboard (Storage → S3 Configuration). Nothing is stored on Vercel.
- `.env` and Vercel need `S3_ENDPOINT`, `S3_REGION`, `S3_BUCKET`, `S3_PUBLIC_URL`, plus
  `S3_ACCESS_KEY_ID` / `S3_SECRET_ACCESS_KEY` (Sensitive on Vercel). `next.config.ts` allows
  `next/image` to load from `S3_PUBLIC_URL`.
- Saving or deleting an image refreshes `/`, like saving the FAQ.
- The FAQ chip falls back to the original picture (`public/BdM8sP8QPHpVTvZLxWbdvJIjAhI.png`) when
  no image is chosen.

## Changing the data model

1. Edit or add a collection in `collections/` and register it in `payload.config.ts`.
2. In dev, Payload updates the schema automatically (it pushes straight to Supabase, which production also uses, so create the migration before deploying).
3. Before deploying, create a migration: `npm run payload migrate:create <name>`.
   Production applies anything new in `migrations/` on startup (`prodMigrations`).
4. `npm run generate:types` refreshes `payload-types.ts`.
   `npm run generate:importmap` is needed after adding custom admin components.

## Changes made to add Payload

- Installed `payload`, `@payloadcms/next`, `@payloadcms/richtext-lexical`, `@payloadcms/db-sqlite` (later swapped for `@payloadcms/db-postgres`),
  `graphql`, `sharp`.
- `package.json`: `"type": "module"` (the Payload CLI can't load the config without it) and
  scripts `payload`, `generate:types`, `generate:importmap`.
- `next.config.ts`: wrapped in `withPayload()`.
- `tsconfig.json`: `@payload-config` path alias.
- Moved the site's root layout into the `app/(frontend)` route group. Payload's admin has its own
  root layout, so going between `/` and `/admin` is a full page load. The share image moved too,
  because at `app/` it no longer attached to the homepage.
- `app/waitlist/store.ts`: the JSON file store (`data/waitlist.json`) is replaced by Payload. It
  held no signups, so nothing was migrated.
- Didn't use `create-payload-app`. It refuses to run while `app/layout.tsx` exists, and its
  template would overwrite `app/(frontend)/layout.tsx` and `page.tsx`. Its admin route files were
  copied as they are.
